1. What the product is

A novel in any language becomes a world you can read, query, watch and, later, fork and write in.

  1. The reading turns the book into an ontology: who each name and each line is, what happens, when, where, who is with whom. Every record cites the book's own sentences.
  2. The console is where the user reads it: every book in any folder they open, the book as published with the reading's marks, its people, places and strands, its problems, the agents beside it.
  3. The world is built from the ontology and played: places as ground and buildings, people moving through them scene by scene, what breaks. It checks the reading in return: physics can say no.
  4. Timelines (the founding goal, §10): canon is one timeline; the user picks a moment and forks a parallel universe; characters can be simulated from what they know at that moment.
  5. Writing (later): the same checks become continuity warnings while typing.

1.2 Principles

These recur through every version; each was the user's call.

  • Rule zero: never ask a model what code can compute exactly (sectioning, counting, matching a full proper name).
  • Few choices for Jev. Jev answers fixed-option questions (a choice, a yes-or-no, a score, a box on a picture) with probabilities. Too many options make it unsure; a question is built so its options are few and meaningful.
  • Structured input. Jev reads a state that can be text, a JSON object or an array; questions point into it by id. Every request is composed by one engine (§5.3).
  • Physics can say no. A proposal that would change the world or the ontology passes the world's laws first (§8.4); what the laws reject goes to review with the reason, never silently applied or dropped.
  • One ledger, one gate. Every proposal and verdict is a record with its source and evidence; no faculty invents its own approval path (§9).
  • Shared sight. Every faculty that decides something about the world decides from the views the user sees; what the user watches is what Jev saw (§12.2).
  • The user's decisions are dated quotes. A design section starts from what the user said and when.
  • Nothing of the book is published. The repository and its pages are public: the book's text, pictures and readings stay with the user (private libraries, .novel/, never exported); models and assets are CC0 or MIT only.

2.2 Two loops, one boundary

Founded 2026-10-21 and still the shape:

  • System 2 (outer): an agent with the skills: ingest, review, query, simulate, fork. It holds the long view (the conversation, the user's intent, consistency over a book) and reviews what is held. It never touches the database or Jev directly, only the CLI.
  • System 1 (inner): the CLI, everything testable without a model: deterministic code plus typed decisions asked of Jev. v3 sharpens it (§8.1): a Jev loop is one bounded job; the agent sets each step's length and corrects between steps.

The boundary is why ingestion can be tested on a golden chapter with a mocked Jev and no spend, and why a skill stays a teaching document rather than code. Pi loads a skill's name and description at start and the full skill only when a task matches, so the front matter's description is the routing signal: kept tight.

"System 2" also names a runtime rule (the user, 2026-11-02): when Jev's answer is below 0.5, the work model is asked the same question with the same composed context (§9.3).

2.3 Storage: the bundle is the truth, Ladybug the engine

Ladybug (formerly Kuzu): an embedded property-graph database: Cypher, columnar storage, ACID, one .lbug file, in-process, with full-text search (BM25) and a vector index (HNSW) in the same engine. It replaced the old stack's Neo4j, Qdrant, Postgres and Redis. Retrieval is GraphRAG in one engine: search finds seed nodes, Cypher walks the causal, presence and timeline edges. Its limits, designed around: a closed schema (src/ground/ontology/schema.ts; a new type is a migration), a fixed vector dimension (the embedding model is in the manifest; changing it is graph reindex), one writer and many readers (a CLI's pattern). All access goes through one OntologyStore interface (src/ground/ontology/store.ts). The npm package ships builds for macOS (both), Linux (x64, arm64) and Windows, not for iOS or Android.

The bundle is diffable, shareable by copying a folder, and engine-independent: entities, relations, events, scenes, timelines, branches, state-changes as JSONL, with manifest.json (novel id, schema version, embedding model and dimension, languages, Jev version). graph.lbug is rebuilt from it and disposable. novel bundle export|import moves a novel. Embeddings were deferred (decision 4): graph first, until Cypher is shown not to be enough (the causality faculty's hybrid search is the one user).

Schema v1. Opaque ids (char_000123, evt_…), names as data (names: [{text, lang, kind}]). Nodes: Character, Location, Organization, Item, Concept, Event, Scene, Timeline, Branch. Relations: CAUSES, CAUSED_BY, PARTICIPATES_IN, PRESENT_IN, MENTIONED_IN, LOCATED_AT, KNOWS, SPEAKS_TO, ADDRESSES, OWNS, MEMBER_OF, STATE_BEFORE, STATE_AFTER, FORKS_FROM, PRECEDES. Event types: dialogue, action, revelation, conflict, movement, decision, introduction, resolution, other. A character's state at a point is a fold of the event stream to that point, never a mutable row (src/ground/ontology/state.ts: emotions and relationships additive and clamped to [−1, 1]; knowledge, goals and possessions added and removed; location replaced).

3. The library: any folder as a workspace of novels

"It scans through every epub or text file in the opened folder, and when we use agent clis to arrange them, they are separated into universes and sorted out, and expandable into Chapters and smaller parts just like how vscode manage repos" — the user, 2026-11-10

3.1 The model

Built (src/library/workspace.ts, folder.ts). The folder the user opens is the workspace, as a repository is the folder that holds its .git. Several folders at once, anywhere on the Mac.

  • The scan finds the books under the folder, skipping hidden folders, node_modules, dist and build. A folder the console adds is scanned for EPUBs by themselves; a .txt or .md file comes in when it is imported (the folder's ⋯ menu), and later scans keep it. A folder keeps its rule (found in workspace.json). DOCX: later.
  • Nothing is moved or changed. The arrangement is one hidden file, .novel/workspace.json, written only by the commands.
  • A file is known by its content. A renamed or moved book keeps its place; a changed one follows its path; a gone one is kept as missing while a universe holds it; the same bytes at two paths are one book with a copy.
  • A universe is a world several books share: a name, a reason (--why), its series, its books in reading order. Files no universe holds are unsorted.
  • The tree: universe › book › chapter › scene (the reading's units; without a reading, the parts the text marks) › cards (a dialogue, an action, a monologue, with who speaks or acts).

Kept apart, from v1's library design (2026-10-25): a source file is not a whole story or an isolated world. Source identity (content hash, file name, edition), series and volume (editorial order), universe and continuity (the shared setting and a compatible canon: adaptations, reboots and branches never silently become one set of facts) and story time (when things happen inside a continuity) are four separate things. Publication, reading, ingestion and in-world order are separate orders.

3.2 The basic layer: no model

Built (src/library/basic.ts, Novel Console 0.6.0). For every book, once, kept in .novel/books/<file id>/basic.json and keyed by its bytes:

Field How
title, author, language the EPUB's package (dc:title, dc:creator, dc:language); a text file's name
series, volume the title with its volume taken out: the Chinese "第 N 卷" form, "(N)", "Vol. N", a number at the end; Chinese numerals read
chapters, paragraphs, lines the reading's own cutters (cutBlocks, sectionBlock)
spoken lines that hold quote marks
pictures the EPUB's image items
names spans that look like names by fixed patterns, three times or more (Chinese and Japanese honorifics and speech verbs, as the name detector nominates them); at most 24

It runs a few books at a time (novel/basicStep) so the console keeps answering. Series found: among unarranged books, titles (volume taken out) sharing most of their character pairs (0.7 of the shorter title's) are one series; the Library offers Arrange for each (novel/series, novel/arrange).

Measured on ~/Documents as a user would add it (0.6.0 from the DMG): 11,770 folders walked in 1.4 s, 29 books and 87 copies found, no text or Markdown file taken for a book, the basic layer of all 29 in 1.4 s, 4 series found.

3.3 Arranged by an agent, one click

Built (0.7.0). Titles cannot say which series share a world, so Arrange with an agent asks the agent open in the chat (the user: "User is free to activate on whichever window using"): Claude Code as claude -p (streamed), or Pi on the work model's key (tools/pi-review/folder-arrange.mjs). Its one tool is the folder's own novel command with the verbs that sort books (basics, show, scan, universe, put, take, and the read-only ones), never read (a paid reading is the user's button), keys, import or link; Claude Code gets it as its only Bash permission, Pi through a scoped bash (folder-scope.mjs) that refuses pipes, joins, expansions, other folders. It follows the folder skill §1: two levels (a universe is one world; series inside it), each book put with --series in reading order, a --why on each universe; what it cannot place stays unsorted. It changes only workspace.json.

Result (2026-11-10): Pi arranged ~/Documents in 79 s with 15 commands, two editions of one series in two languages joined; the user counts arranging universes as done ("agent successfully put them in the exact order I needed").

3.5 Readings, links and the universe

A reading gives a book its symbols. A reading made by v2 is linked read-only; when its stored source is another extraction of the same book than the file gives (volume 1: 124,716 characters stored, 129,322 from the EPUB), the book is shown as that stored source, because the reading's sentence ids cite it. A one-click reading is made inside the folder (§4.5).

The same entry across books is matched today by a shared name. Left out of v3 The universe-level systems v1 built are the design for doing it properly, each one list per universe that every book's records are placed on: universal EM (one character list), the universe calendar (one clock) and the universe causal ledger. In v3 they belong to a universe of the workspace, written by its readings and reviewed through the gate.

3.6 v1's library, for the record

Superseded by the folder workspace (v3). v1's novel library init|add|show|evidence kept content-addressed sources (doc_<sha256>) and a versioned catalog.json of universes › continuities › series › assignments, each confirmed or unresolved (unresolved ones stay out of scoped results). Plans were evidence-gated: membership and order were only as good as their quotes, verified at exact offsets. It was federated, never fused: each source got its own workspace (block ids restart at b0001 per file, so a shared workspace would collide), and identity failed closed: Jev and the agent see labels, code resolves labels to ids, ambiguity is refused. v3 keeps the content addressing, the separation of the four orders and the per-book stored source; the folder replaces the catalog. Its live view (series organised in the orbital explorer, durable facts → public snapshot → SSE) went with the playground (§4.9).

Where novels differ. 5.2 Who is who: EM, EM² and the universe

EM answers which entity a name is, once; EM² answers who this is, here (the user, 2026-10-30). After the first full run 137 of 174 people had only descriptions for names, and 1,789 of 2,419 world sentences named no one (我, 你, 他, or no word at all). The same words point at different people (少女 is one person in one scene and another in the next), so EM² is asked where the words stand, a scene at a time, and the unnamed are slots of the scene that later lines may choose.

The introduction (2026-11-05: "are we using the introduction parts to leverage our overall understanding?") is a step of the reading: each cast entry and synopsis paragraph is a standing fact that every EM and EM² request about that person carries; an epithet's quoted names become theirs before the book is read; two people the introduction names as one are merged; a plate page's people let the cropper bind a face by elimination.

Labels, not ids. Jev and the agent see readable labels; code resolves a label to an id; ambiguity fails closed (v1, decision 24): a full label is matched literally, never a fragment.

Universal EM: one character list per universe

Left out of v3 Built in v1 (2026-10-28) and not carried into the v2 reading or v3's workspace, which matches the same person across books by a shared name.

Who a character is used to be decided in five places that never saw the same candidates (an exact name index, a per-scene birth check, the review gate, a structural pass after apply, and novel match); one person under a full name, a short form and a description became three records, and a person met again in a later book became a new one. Universal EM replaces all five with one mechanism over two inputs: the universal recommender (for a scene, who it could be, from one pool: this book's people, the universe's other books' people, and the names just found), scored as the cast recommender (named in the scene 1.0, nearby scenes, the chapter, the book) plus a small prior for the universe's central people; and the newly found names with their passages.

  • A full proper name owned by one candidate binds by code, within a book and across books. Anything else is one Jev choice per name over its passage among the recommender's best.
  • Named buildings and large things go through the same two systems (building EM: one building, one lot).
  • novel em show <book>: the book's people, those shared with other books, and the open questions.
  • Measured (2026-10-28, three reviewed volumes of one universe, offline, against seven duplicates found by hand in the third): old EM merged 0 and missed 7; universal EM merged 3 automatically, raised the other 4 for review with the right partner, missed none, made no wrong merge, and joined 16 people across the three books by full name. The one wrong review item rested on a shared description, which is why such matches are reviewed rather than merged.

For v3: one character list per universe of the workspace, written as each book is read (the v2 reading's EM pool widened to the universe's other books), so references, Characters and strands join across a series; corrections through the gate.

Before it: alias at birth (a description finds its owner before minting) and fragment at birth (a name fragment, 食蜂 for 食蜂操祈, checked by one strict Jev round before a new person is minted; naive substring folding is dangerous: 御坂 is a family) and the structural EM backstop (score ≥ 0.6 with ≥ 2 shared scenes or ≥ 3 shared neighbours) Superseded by universal EM (2026-10-28, PR 76).

5.4 Story time

Built (src/reading/time.ts). The time tree: story › year › season › day › part of day, the past a branch of its own (flashbacks); ordered, so its left-to-right order of scenes is the story's order, while reading order may differ (a flashback sits in the past branch; a scene told later can come earlier). Where the story goes back on the tree without a flashback the order law is broken, and treeConflicts records it. Option meanings are asked once a request.

v1's time and place faculty (phase 1, 2026-10-26: TimePoint entities, Jev flashback roles, story order kept strictly apart from reading order) and its benchmark of story time as a partial order (scenes before, after or parallel; novel eval story-order; 2026-10-27, measured, not built) are the ancestors: keep reading order separate from story time, and keep parallel, unknown and conflicting chronology rather than invent a total order.

5.8 Causality

  • Inside a book: removed (v1's world-first design, 2026-10-29). The world is continuous, so for any event the world log gives its lineage with no model call: the events before it on the clock that share its actors, the events at its place, the dialogues its actors heard, the state changes that led into it. Lineage shows what led up to an event; it does not claim that A directly caused B.
  • Left out of v3 Across books: the universe causal ledger (v1, 2026-10-25). novel causality universe: only reviewed library assignments enter; pairs share one continuity; endpoints are canonical events or dialogue cards qualified by their source (doc_<sha256>::<local id>); nomination by names only (no embedding leg); a Jev sweep feeds independent review; accepted links go to a separate audited ledger, never merged into a book's graph. Cross-scene retrieval (v1, 2026-10-26): events and cards are equal search units; candidates strictly earlier in story order, outside the effect's scene, with no existing path; embedding matches above cosine 0.5 ranked by earliness, top 32; Jev asked for direct support with a succession veto; ranking, precedence and reachability are never causal proof. The laws, as matrices. Let C be the places' containment matrix (C[i][j] = 1 when j directly holds i): one parent each (one choice, never a set), n − r links for n places and r roots, no loops (C is nilpotent), graded (a parent is larger than what it holds, which alone cuts most candidates), leaves exist (unnamed places are leaves under a named one), one address (where is a path; two places relate through their lowest common ancestor). 6.2 The map: render units (v3)

"Walk time dependant isn't reliable. Transportation methods varies largely across different novels. What we can do is a most rendered entity. The director or agent or some cast, will determine the largest continuous render units in the story. For example planet level and a scene happened in the space ship are the same level. Designed, nothing built; a first design to correct. It replaces v2's fixed place scales and both drafts of places as open layers (§6.5).

The idea. The map is not a hierarchy of sizes. It is a set of render units: each the largest space the story plays in without a break, rendered as one continuous whole.

  • Units are peers. A planet the story roams and the inside of a spaceship are the same level. What makes a unit is continuity of the story's rendering, not size and not how anyone travels.
  • Each unit has its own scale, set by what acts in it and how far the action reaches: people in rooms and streets; ships and fleets round planets; planets in a battle that destroys them. Detail inside a unit is laid out on the unit's own ladder.
  • One thing may be seen at several scales. A planet is the ground of a unit when a small scene plays on it, and an object inside another unit when fleets destroy planets.
  • Between units the story cuts. No walk or travel time is assumed; what the text says of a journey (who, by what, how long) is kept as told and played as a cut, or inside a vehicle that is a unit of its own.
What it is Examples
the anchor the entity rendered whole: the most rendered entity of a stretch of story a city, a planet's surface, a ship, a castle, a battlefield in space
the actors' scale what counts as a body in it a person, a mecha, a ship, a fleet, a planet
the reach how far the action goes, counted in actors' bodies, not metres a room is a few people across; a battle a few hundred ships
the ladder the unit's own levels of detail, from the actors' scale up to the anchor person, room, building, street, city; ship, formation, orbit, system
the stretches the runs of story played in it

Only the actors' scale ties a unit to anything absolute: a unit whose actors are people is built at human size, as now.

Found, not configured. A pre-film cast (or the agent, in a pass before terrain) proposes the units from the story's own evidence; the agent confirms or corrects, each write with a why. Evidence: runs of scenes whose people move without a break in the telling (the story stays); a move told as a journey, a jump in place with no way between, a change of what acts (it breaks); the entity most scenes stand in or look at (the anchor); what the text says holds what, and what it shows from outside.

Links between units. Seen from: a unit appears inside another as an object at that unit's scale (the ship in orbit over the planet); the link names both views. What happens to the object happens to the unit: a planet destroyed closes the units on its surface; a ship boarded joins its unit to the boarders' strand (this is where strands and the carry across books meet the map). Every other move is a cut.

6.3 Strands: groups in envelopes

"The idea of strand is a timeline performed by a group of people in a limited, enveloping area." — the user, 2026-11-09

What it is What it means for the engine
the group the people performing it a person is in one strand at a time; their state (where they stand, since when) is the strand's (L1)

Strands by interaction (2026-11-09). Walking the scenes in story order: the group is the people acting (and anyone an action of theirs is aimed at who is there); a split is part of a group acting while the rest next appears out of view of them; a union is an interaction between strands (one conversation, one action, one event), the strand begun first keeping its id; strands acting in one scene with no interaction stay apart (beside); a strand lands only if its group has a dialogue or an action in its next segment, else it folds back; a union is refused only when both sides go straight back apart; a flashback is a strand of its own in the past: it plays from the past's state and hands nothing on. A strand not closed by a union is open; at a book's end the open strands are what the carry reads. Volume 1: 3 strands, 1 split, 2 unions, 4 folded, 0 refused.

Physics per strand: the world's damage is a layer per strand over the built world (strand-layers.mjs); when strands unite their layers merge. Re-strand after smoothing (smoother/restrand.mjs): a unit's acting people chain into one group within earshot, and the text's interactions join them at any distance (beyond earshot it is an apartTalk fault).

All design revolves around strands (the user, 2026-11-03: "there should be no scene level processing"): hand-overs are in story time (a person's from is the last container they were in in story time), strands become forks of story time, and the timeline the console draws is the strands' graph.

6.4 Across books: the carry, per strand

Built (M16, engine/world/carry.mjs, novel strands; the user, 2026-11-09: "the cleaning should be per strand, not per book ... what if the next book returned to a non finished strand?").

  • A nominated place is permanent: its slot is its own for good, its name returns to it in every later book, with every book's damage to it.
  • A strand's shares and damage live as long as the strand. An unnamed mention's share and the damage to a building that is not nominated belong to the strand they happened in. At the next book's reading each open strand of the last book is inherited (its damage stays) or closed (what it broke stands whole again); the main agent may override with a why (novel strands register|inherit|set|keep|show).

  • A strand does not end at a chapter's or book's end (2026-11-02): continuity holds to its last scene in whatever book that is.

7.2 Borrowing and spawning by type

The user's design, 2026-11-01: a city should stop growing with every scene.

Built (M0–M5, M11, M16). Every unnamed mention used to become an area of its own, so a city grew with the number of scenes. Instead:

  • Every type has a spawning configuration (config/terrain/: city.json, district.json, street.json, building-types.json, heights.json, composite.json): what an area of that type spawns one level down. A metropolis spawns 2 CBDs, 3 dwelling areas, 1 industrial area; a CBD 2 avenues, 1 centre, 1 station front, 1 square, 1 shopping street; a street its buildings by density (a shopping street 49 a hectare, a quarter shops). A count is a number or a range picked once per parent by a seed.
  • Slots. When an area's type is decided it spawns its children as slots: typed, unnamed, real manifolds of its parent's ground, placed by the parent's topology (rings: how far from the centre each kind sits; pairs: kinds that sit near or apart), blending into their neighbours. A city is a combination of manifolds over time.
  • Borrowing. A mention typed by Jev borrows a slot of its type in its parent (a name for good; an unnamed mention shared within its book). It spawns a new slot only when it can borrow nothing. Level by level (every city, then every district, street, building), in narrative order.
  • The objective (the user's law): borrowing and spawning make the total distance the characters must go between their scenes as small as can be: Σ over pairs of places t(p, q) · d(p, q), where t counts the characters' trips. Minimized per level (a small quadratic assignment: greedy, then moves that lower it), with guards against what it gets wrong. It converges: a parent's slots are bounded by its configuration, so the city stops growing.
  • Heights: a manifold's height is its average; every type has a minimum standard height and Jev is asked an offset from it; the minimum gate (heights.json) refuses any slice under a type's least height; the text's own measures (五十层, 两百米高, 地下三层) are offered as a slice of their own; floating objects ask first how far they are from the ground.
  • The building level: a street's buildings are the lots its form builds; a building's type is found among some ninety by its name and its scenes' sentences (a local embedding model and words; Jev chooses among the ten nearest when the search is not sure); composite buildings (a shop, a restaurant, a cinema) are parts of a host where the characters' travel is least; tall buildings above 100 m grow thicker (no side under height / 8) and widen the streets round them; some places only make sense among tall buildings (a boulevard of towers).
  • Landmark shells: buildings the text names stand on their own lots with their own shells.
  • The map's log by book: every change logged with the book, so a book can be played again as it grew.
  • Damage and sharing: a shared slot is one place through time (§6.4 for across books).

It replaced sampling pools (pools.ts: pool areas, members, even picks), Superseded.

8.1 Smaller Jev loops, an agent keeping the long view (v3)

Designed (the user, 2026-11-10): "make the runtime jev loops smaller. Jev miniloop of casts are good, but they lack fundamental ability to correct itself in long term. It's errors stack and our final effect goes out of control. But jev does have the ability to place spatial things in 2d and do structural extractions at high-speed, which we don't want to abandon."

What went wrong in v2: an answer of Jev's became the input of the next for a whole volume (516 calls in W15) and nothing looked back. A fighter sent up an office tower at unit 14 was still there at unit 26; a line credited to the wrong person walked the protagonist 40 floors up; 28 units of W15 played in the wrong district.

  • A Jev loop is one bounded job on one 2D frame, a handful of questions. The agent decides the step's length (the user: "The agent can decide the step length of the miniloop"): a card, a scene, a stretch of a unit; shorter where the last steps went wrong, longer where they held. Its inputs are the text and checked state, never Jev's own earlier answers unchecked.
  • Every step starts from the text again: who is there and where the text puts them. An error cannot outlive its step.
  • Every answer is checked at once by code (the laws as assertions): a failing answer is asked once more with the failure shown, then left to a rule.
  • The long view is the agent's: after each step it sees what was placed and what the checks say, corrects (a pin, a note to the next step) and sets the next step's length, before it runs.

8.5 Smoothing: back-propagation as Bayesian smoothing

Legacy (Track B, 2026-11-02/03; engine/smoother/).

"Every character or object is a particle: its states are a distribution, not a fixed set ... Back-propagation in the particle path integral is Bayesian smoothing: it turns discrete, uncertain observations at intervals into continuous clouds." — the user, 2026-11-02

  • Ground truth is ranked: every position in the world log carries how it came to be (a pin above all, then the text stated, implied, a rule, a default).
  • When a new anchor lands for someone at a moment in a strand, the history is revised backward, changing the history least in space and in destruction energy. The path integral's weight e^(−S/T) is a Markov process, so its backward message is a smoother's: a moment's cloud is forward × backward. We define the action: S = S_walk + S_seen + S_talk + S_frame + S_events.
  • One observation, several updates: each observation gives several state facts, some subtle and sure, some confirmed.
  • Back and forth in a second pass (2026-11-07): a walk that goes out and comes straight back is read again.
  • Smoothing is per strand; L18 (destruction) and L19 (places) as smoothed states.

8.6 Figures that act: the action animation system

Designed (the user, 2026-11-12: "This is actually the actor cast. But this might need to built on top of the action animation system. We need actionable figures to be able to check."). The ground the actor cast (§8.7) stands on.

  • What a person is today: a glowing pawn with a name (engine/view/strand-demo.html), a node on the walk grid and nothing else. It has no body, no facing, no pose; a walk is a path, a blow a line from one pawn to another. Nothing can be asked of a pawn but where it stands.
  • A figure is a person with a body: a humanoid rig sized by who they are (a child, an adult, the settei cast's build and height), and at every moment of the run a state the engine can read and check:
    • where it stands (as now), which way the body faces, where the head and eyes look;
    • its pose: standing, walking, running, sitting, crouching, lying, falling, climbing, carried, riding;
    • its hands: what it holds (the things' holders the director already tracks), what it reaches for;

  • Driven by what the run already records, by rule first: a walk's path and pace choose the gait; in talk a figure faces whom it speaks to; in a fight it faces its opponent, and each exchange (close, line or area; hit or stopped) is a strike and its reaction; the transport ties put a rider on its carrier and the carried in arms; an ability in use (a leap, flight) is its own motion. Where the text says where someone looks ("he looked up at the roof"), a cast says so; the rule fills the rest.
  • Actionable means it can be asked: is she facing him, can he reach her hand, is anyone sitting on the bench, and above all what does this person see (§8.7). Each answer is code on the figure's state, never a model.
  • Checked as the rest is: the laws as assertions on figures (eyes at the body's height, no limb through a wall, a seated figure on a seat, a held thing in a hand), retaken as the miniloop retakes (§8.1).
  • Drawn on the page with three.js's skinned meshes and animation mixer; the render protocol for the world client (§12.1) carries a figure's state (pose, clip and its phase, facing, gaze), not meshes.
  • Where the figures and clips come from: free licensed rigged figures and clip libraries (CC0, as the model packs are, §7.6), fetched only with the user's OK; clips under licences that forbid sharing them cannot go in this public repository.

9.2 One gate for every faculty

Built (v1, settled 2026-10-26, decision 26). No new faculty or flow may create its own review or approval gate. One staged contract, across book, universe and library scopes:

  1. SHOW: the packet's facts in bounded pages, each fact's meaning, its evidence pointers, the revision digest.
  2. EVIDENCE: the original evidence behind a fact, paged.
  3. DECIDE: per-fact verdicts (accept, hold, reject), each with a source-grounded reason, under the packet's revision.
  4. APPLY: accepted, supported facts materialize; held and rejected stay out; unreviewed facts stay held by default.

The unit is the per-field fact, bound to a revision digest over packet, source and canonical context (novel review show|evidence|decide|apply). Precision first: source-valid text organization (segmentation, dialogue boundaries) is validated by code; consequential claims are reviewed. Logged interventions are not accuracy: an accepted replacement is an intervention, not proof the new value is right.

10. Timelines, forking and simulation

Left out of v3 The founding goal ("parallel-universe story forking", "character simulation", 2026-10-21). v1 designed it and built its foundation; v2 and v3 have not taken it up. It belongs to v3 after the world client: the console is where a user would pick the moment.

Built: the types (Branch, CharacterStateAtPoint in src/ground/ontology/types.ts; the FORKS_FROM relation and the Branch table in schema v1), novel timeline list|show, state changes persisted at apply time (state-changes.jsonl) and the deterministic fold (foldStateAt, novel state). Not built: novel fork create, novel simulate.

  • A fork is a pointer, a snapshot and deltas: a branch stores its fork event, a fold of the characters' states at that point, and only its own new events. No copy of the canon prefix, so branches are cheap and a user can keep many. Canon is never mutated; deleting a branch loses nothing canonical. A branch may fork from a branch.
  • Browsing is importance-led: the fork-point browser lists events by chapter with their importance, so interesting seams surface first; any event is a legal fork point. Jev assists, never decides: how divergent a fork here would be; which existing branch a conversation is closest to. The user picks the point.
  • State is a fold, never a row: emotions, knowledge, goals and relationships are computed by replaying events to the point. Move the point and the person changes, on canon and on every branch alike.
  • Ignorance is a feature: the fold is a wall. Facts from later chapters or other branches are not in the prompt, so a simulated character cannot leak them. Voice comes from the character's own attributed lines (forms of address, tics, sentence length), not a written persona.
  • Jev referees: in character (yes or no), would say this against alternatives (a choice), drift (a score).
  • Talk can become canon for a branch: when talk turns into story, its events are branch deltas proposed through the same gate (§9); simulation never silently rewrites a world.
  • Story time must be honest first: forks and folds need an explicit policy for events whose order is unknown, not an invented total order (§5.4).

For v3, open: forking at a moment of a strand (the console's Strands view as the fork-point browser); whether a branch replays the world from the fork's world state (strands and the carry make that possible); how a simulated conversation is played in the world.

12. The world client and the live view

12.1 A native engine behind a render protocol

"I'm thinking about whether we should build a real vscode extension activatable unity based game engine frontend. The first reason is our browser is very easy to get stuck, two is we might want to integrate vr and ar versions in the future. You can decide." — the user, 2026-11-10

Designed (decided 2026-11-10): Unity, as a render client the console launches; the world engine is not ported.

  • One world server, several render clients. The simulation stays in TypeScript on Node (terrain, the director, the laws, structures, blasts) and is the only truth. It sends the world to clients over one versioned render protocol: a unit's ground, lots, shells, props, people and their moves, as a compact stream of changes.
  • The Unity client builds everything from that stream in code (no hand-made scenes; the world is procedural), with the engine's instancing, culling and threads. The console starts it as its own window and ties it to the reader over a local socket: a line moves the world, a click in the world finds the line.
  • The web page stays only where it must: today's three.js page, fed by the same protocol, for Jev's camera (its 2D maps and stills) until the Unity client can take those, and inside the console as the world view meanwhile.
  • VR and AR later, from the same client: a headset build is another target of the project.

Why (checked 2026-11-10): the browser gets stuck partly because of our data path (one thread, no workers; a full run's page was an 89 MB JSON file in W15): the protocol fixes that for every client, and a native engine adds threads, instancing and culling. A native view cannot be docked inside a web view, so the client is its own window. Unity's Render Streaming has had no release since December 2024 and its WebRTC package was reported deprecated in August 2026: not a base for streaming into a panel. Unity Personal is free under 200,000 USD a year; Vision Pro needs Unity Pro (about 2,300 USD a year); Quest and phone AR do not. Godot is the open alternative (free, text-based, good Quest support; weaker on Vision Pro and phone AR). An agent can build Unity without its interface (C# and project files are text; builds and play-mode tests run from the command line), once the editor is installed. Costs: two clients on one protocol, a slower build loop, a proprietary engine (the cache folder never committed).

The first step is a proof with a way out: the render protocol for one unit, and a Unity client drawing volume 1's city from it with its people moving, measured in frames a second against the web page on the same data. If it does not clearly win, the protocol stands and the client can be Godot or the web page with workers.

13.4 Errors an agent can act on

Built (after rustc's diagnostics). How state flows into the ontology

  1. play: the director changes its state card by card (positions, exchanges, feelings, holdings, buildings) (engine/director/director.mjs)
  2. world log: each change a record, append-only, with its rank (pinned, stated, met, answered, ruled) and source (engine/log/world-log.mjs)
  3. laws: checked as it plays (held, amended) and over the whole run afterwards (engine/laws/laws.mjs)
  4. smoother: positions and presence back-propagated: the least-action history and its clouds (later: feelings, as additive states) (engine/smoother/)
  5. ledger: the run's proposals to the ontology, each with its evidence and the laws' verdicts (engine/log/write-log.mjs)
  6. gate: applied by canon where a law checks it, held for the review (Pi) otherwise; some state stays with the run (engine/review/canon.mjs, review.mjs)
  7. canon: written into ontology/*.jsonl (last write wins by id), every write logged in canon.jsonl and undoable; the graph rebuilt (engine/review/canon.mjs)
  8. next run: the review's answers become pins; canon, pins and the smoothing are where the next run starts from (engine/review/review.mjs)
  • applied: written by canon without review: a law checks it and nothing broke
  • held: held for the review first; written once answered (some move to applied once audits show they are right)
  • run: kept with the run only (its records, the page); never in the ontology

Street × street: may they adjoin?

Compatible kinds may touch, not lie over each other: a box mostly over a compatible kept place is asked again, and compatible parts still overlapping are moved beside each other (the pool expanding, nothing vanishing). 17.5 The reading's output

The v2 reading's data, field by field (engine/reading/read.mjs writes it as YAML under <out>/v2/ and as data.json). Every record is keyed by, or made of, sentence ids: the sentence is the smallest unit.

# The v2 reading's data (src/reading, docs/v2/world-engine-v2.md §2.0). Every record is keyed by, or made of, sentence ids:
# the sentence is the smallest unit. engine/reading/read.mjs writes these as YAML under <out>/v2/ (and data.json, the same
# data for tools), with log.yaml for the run.

sentence:            # from intake (sectioning), never a model
  id: string         # b<block>_s<n>, stable for the same text and block size
  text: string
  block: string      # b0001 …
  chapter: integer

picture:             # the album (EPUB illustrations), anchored on a sentence
  file: string       # assets/ill_0001.jpg
  sentenceId: string

scene:               # scenes.yaml — scene tiling (Jev, start selection)
  id: string         # scene_000001
  block: string
  chapter: integer
  first: string      # sentence id
  last: string       # sentence id
  sentences: integer

kind:                # kinds.yaml — one per sentence (Jev, one structured document a window)
  kind: [spoken, thought, fact, action, environment, narration]
  turn: number       # 0..1: does the carrier change here (who speaks it, who acts in it, or what it is about)
  confidence: number
  was: string        # action, where the action rule made it narration (nothing that matters acts in it, by EM²)

card:                # cards.yaml — runs of one kind, a new card where the carrier changes; exchanges and monologues over them
  id: string         # <kind>:<first sentence id>
  kind: [spoken, thought, fact, action, environment, narration, dialogue, monologue]
  home: [world, ontology]   # dialogue, spoken, action, environment → world; thought, monologue, fact, narration → ontology
  first: string
  last: string
  inside: [string]   # dialogue and monologue cards: the cards inside them
  block: string
  entities:          # the card scan (System 0): who and what the card names, and where
    - id: string
      at: [string]   # sentence ids
  people:            # who is in the card: named (scan), speaks / acts / addressed (EM² roles), described (EM² references)
    - id: string     # a person (char_), an unnamed one (slot_), or a named thing or place that acts (item_, loc_)
      how: [string]
      at: [string]

detected:            # a listed string, typed (em.yaml holds each with its outcome)
  key: string        # n1, n2 … within its batch
  text: string       # word for word as the passage writes it
  type: [person, crowd, object, routine, weapon, vehicle, region, city, district, street, building, room, spatial, concept, time, none]   # a place by its scale; place: an open place of a reading before the scales
  category: [person, crowd, thing, place, concept, time, null]   # a crowd is never a name: EM² places it; routine (an everyday thing) and spatial (where someone is): null
  proper: number     # 0..1: a proper name (a name anywhere) or a description (a name only where EM said it)
  sentences: [string]

em_result:           # em.yaml — per batch (its first sentence id), per detected string
  outcome: [exact, alias, new, time, description, routine, spatial, skip]   # description: of a person, a crowd, an unnamed vehicle, weapon or place (EM² resolves it); routine: an everyday or unnamed thing, no entity; spatial: where someone is (spatial.yaml)
  sentences: [string] # description and spatial: the sentences that hold it
  facts: [string]    # the facts Jev was given for it (fact ids): the latest about its candidates, and those holding it
  owner: { answer: string, confidence: number }   # a concept: whose it is, as asked in this batch (a person id, many, none)
  entity: string     # the chart entity (or time node) it is
  candidates:        # the recommender's best three, by nearness, frequency and shared names
    - id: string
      score: number
  answer: string     # Jev's choice: a candidate, another string of the batch (n…), or new
  confidence: number
  unsure: string     # new below the threshold: its best candidate, for the world engine's second EM

entity:              # chart.yaml — the ontology's identities (canon ids: char_, loc_, item_, concept_)
  id: string
  category: [person, place, thing, concept]
  type: string       # the type it was first typed as
  names: [string]    # every name EM gave it
  proper: [string]   # its names anywhere (exact match, the card scan)
  first: string      # sentence id
  seen: [string]     # every sentence it appears in
  owners:            # a concept's: whose it is (a person id, or many), from the sentence it was said in
    - { id: string, from: string, confidence: number }

time_node:           # chart.yaml times — EM for times is the calendar's (later)
  id: string         # time_000001
  text: string
  seen: [string]

context:             # contexts.yaml — what the world engine is given for each scene
  scene: string
  cards: [string]    # its world cards
  before:            # the scene before's cards of the same kinds, in order
    dialogue: [string]
    action: [string]
    environment: [string]
  recommended:       # the people the recommender expects (the last three scenes)
    - id: string
      score: number
  facts: [string]    # the latest facts before it (fact ids)

pick:                # one EM² answer
  id: string         # the person, slot, thing or place it settles on; null: no one, or no one sure (below 0.5)
  answer: string     # what it settled to: an id, unnamed, none, time (the story goes back in time); through a description, its answer (an id, general, none)
  confidence: number
  via: string        # the description of the passage the answer went through

role:                # roles.yaml — per spoken or action sentence (EM²)
  kind: [spoken, action]
  who: pick          # who says it / who or what acts (a person, a crowd, a named thing, a vehicle, a weapon, a place), or time
  to: pick           # spoken only: who it is said to

reference:           # references.yaml — a description of a person, a crowd, a vehicle or a weapon where it stands (EM²)
  text: string
  type: [person, crowd, vehicle, weapon]
  scene: string
  sentences: [string]
  entity: string     # a person (or a named vehicle or weapon), a slot, or null (in general, or none)
  answer: string     # a person or slot id, new, general, none
  confidence: number
  unsure: string     # not sure: the person it leaned to (a slot was opened)
  facts: [string]    # the facts holding it that Jev was given

slot:                # slots.yaml — an unnamed person, crowd, vehicle, weapon or place of one scene; never anyone's name
  id: string         # slot_<scene number>_<n>
  kind: [person, crowd, vehicle, weapon, place, building, room]
  in: string         # a place, building or room: the named place EM² said holds it
  scale: string      # an unnamed open place (kind place): its scale as typed (street, district, …)
  scene: string
  label: string      # the description that opened it
  names: [string]    # every description that meant it
  sentences: [string]

habit:               # slots.yaml habits — what a description has meant (a prior for later, never an exact match)
  text: string
  entity: string
  count: integer
  speakers: { person id: integer }   # in whose lines

fact:                # facts.yaml — the fact ledger: the source of truth for EM and EM², in reading order
  id: string         # fact_000001 …
  card: string       # the fact card
  first: string
  last: string
  sentences: [string]
  order: integer     # its place in reading order
  time: string       # the latest time node at or before it
  period: string     # the story period it is told in (time.yaml)
  story: integer     # that period's story order: the ledger ranks facts by it, then by reading order
  about:             # who and what it is about
    - id: string
      via: [name, description, concept]   # a name in it (the chart's names at the end), a description EM² resolved in it, or the owner of a concept it names

log:                 # log.yaml — the run
  sentences: integer
  wallMs: integer
  paidRequests: { jev: integer, work: integer }
  steps:
    - step: string
      requests: integer
      ms: integer
      inputChars: integer

time:                # time.yaml — story time (src/reading/time.ts)
  words:             # every time word where it stands
    - key: string    # <sentence id>:<start>
      text: string
      sentence: string
      family: string # date, clock, relative-day, relative-span, time-of-day, holiday, season, weekday, past-marker
      gloss: string  # its value, read by the time lexicon
      role: [ADVANCE, FLASHBACK, RETURN, REFERENCE]
      decidedBy: [rule, jev, default]
      confidence: number
      downgraded: string   # an unsure move or flashback kept as a mention
  periods:           # story periods: a time word that set the scene's time, until the next
    - id: string     # time_<sentence id>_<start>
      label: string
      flashback: boolean
      toldFrom: string     # a flashback: the present period it was told from
      date: { year: integer, month: integer, day: integer, derived: boolean }   # stated, or derived from stated words; never guessed
      storyIndex: integer  # story order (a flashback before the period it was told from)
      scenes: [string]
      when: string   # on the calendar: "Year 1 · 12-24 · evening", or "between …"
  scenes:
    - scene: string
      periods: [string]
      flashback: boolean
      inherited: boolean   # no time word of its own: it carries on
      when: string   # the caption: when it takes place
  calendar: { entries: [calendar entry], conflicts: [{ ref: string, note: string }] }

places:              # places.yaml — the place tree (src/world/rules/places.ts)
  places:
    - id: string     # a named place (loc_)
      parent: string # the named place that holds it, or null
      by: [name, stated, em2, jev, none]
      confidence: number
      scale: [region, city, district, street, building, room, null]
      scaleBy: [typing, name, holds, tree, null]   # holds: a step above what it holds; tree: raised over an open place it holds
  slots: [{ id: string, kind: string, scene: string, label: string, in: string, scale: string }]

spatial:             # spatial.yaml — spatial words: where someone or something is (src/reading/spatial.ts)
  - text: string     # 地面, 地下, 屋顶上 … word for word
    sentence: string
    scene: string
    level: [underground, street, inside, roof, wall, sky, null]   # the world's level it points at
    who: [string]    # who or what acts or speaks in its line (EM²'s role, else the card)

Merge gate — blocks roll, proposals wait, the main agent decides

status: implemented repo: src/solidifier/merge/ · src/digger/processing/blockProcessor.ts reviewer: the main agent (System 2)

The processing model of the whole system, and the one gate every faculty shares (decision #26). Ingestion rolls block by block — chapter, or long block. For each block, sectors 01–08 produce proposals; this sector decomposes them into per-field facts — identity, alias, actors, presence, mention, location, turn, dialogue-member, relation, state — each with a readable meaning, its original evidence, and a revision digest. The main agent — with all its memories and capabilities — reviews through one staged protocol: novel review show (read the facts) → novel review evidence (read the evidence) → novel review decide (stage per-fact accept / hold / reject with a reason) → novel review apply (publish). Decide only stages; apply explicitly publishes. Then the next block rolls, until the novel is done.

InputsAll proposals for one block (patches 02–06 + extraction 08 + post-apply faculties like 08b), each decomposed into facts with confidence + provenance + evidence
OutputsStaged decisions in the review state + audit history; on apply, only accepted, supported facts materialize via OntologyStore (10) — unreviewed facts stay held
Depends on07 Miniloop engine, 08 Extraction, 08b Time & place (post-apply), 09b Causality (proposals)

Settled principle: every faculty shares one semantic gate

No new faculty or flow may create its own review/approval gate. Ingestion, local causality, universe causality and library organization use novel review show|evidence|decide|apply. Choose storage with --scope book|universe|library, not a different agent workflow.

Every assertion has a readable meaning, original evidence and a revision. Decisions use factId, accept|hold|reject and a reason. Decide only stages; apply explicitly publishes. Unreviewed facts stay held. Domain validators add causal direction, endpoint and cycle checks without bypassing the common evidence, audit and stale-revision safeguards.

New faculties register assertion/provenance support and validators with the existing storage adapter. Unsupported packets fail closed; never create a new approval command to work around that. See the shared contract and compatibility boundaries.

The four steps — and what each one cannot do

SHOW

Read the packet's facts in bounded pages: each fact's meaning, its evidence pointers, and the revision digest. Read-only — showing stages nothing and applies nothing.

EVIDENCE

Read the original evidence behind a fact, paged. A causal accept requires the full assertion set and both endpoints' evidence to have been read — otherwise the fact cannot be accepted, however confident it looks.

DECIDE

Stage per-fact verdicts — accept, hold, or reject — each with a source-grounded reason, under the packet's revision. Deciding writes review state and audit history only. It publishes nothing.

APPLY

Publish the staged decisions: accepted, supported facts materialize; held and rejected facts stay out; unreviewed facts stay held by default. A second apply is rejected — duplicate-apply protection — and a changed revision voids the staged state.

The old block verdicts survive as pre-approval tools, not as the protocol: hold pauses a packet, and revise names the parts the agent doubts so the miniloop re-runs only those parts and returns a revised packet. Neither publishes anything.

Design details

  • Why an agent behind the gate: the miniloop is fast and local, but it cannot know that a nickname in chapter 30 belongs to a character introduced in chapter 2, or that two similar names are twins. The fast system proposes; the context-rich system decides.
  • Enforced in code, not convention: decide writes review state and an append-only audit history — never canon. Apply requires staged decisions under the same revision, evidence coverage for every accepted fact (full assertion set and both endpoints for causal facts), and rejects a second apply. A changed revision voids the staged state. In the scoped Pi host, legacy approval spellings are blocked with an actionable migration error pointing at the staged protocol, and source-less legacy packets fail closed instead of finding a shortcut.
  • The audit trail: every proposal carries block ID, sentence IDs, producing patch, and confidence; every decision carries its fact id, verdict, and source-grounded reason in the review state and history.jsonl (private review dir, never in the bundle). Every node in the graph can answer: which block, which sentences, which patch, what confidence, whose approval.
  • One gate, three scopes: book, universe and library packets all flow through the same lifecycle — show, evidence, decide, apply — with storage adapters supplying domain validation (causal direction, endpoint and cycle checks; library plan atomicity). A new faculty registers its assertions and validators with the shared gate; it does not get its own approval command (decision #26, enforced: unregistered scopes throw).
  • A natural end: when the last block the user asked for merges, ingestion is done — the loop terminates on the work, not on a timer.
  • Review is staged (decided 2026-10-22): before the agent deliberates, System 1 pre-reviews the batch itself. Entity matching is the first stage: code nominates duplicate pairs (shared forms, script-variant folds, containment, near-identical forms), and one batched Jev checklist per batch (same entity? treated as distinct? mere form variant?) routes them — confident pairs arrive as ready merge fixes, only unsettled pairs are raised to the agent as real requests. Duplicates are the known failure mode of extraction; they are settled at the gate, not inside the extractor.
  • Pointwise before wholesale: small errors are fixed pointwise by the agent over the bundle (novel fix merge|rename|add-form|relate|unrelate|remove-entity|remove-event), each fix audited in maintenance.jsonl with the graph rebuilt after it. A block is never re-run for a typo.
  • Recall nominates the chain: when an entire subtree is wrong midway, the agent traces the cascade to the earliest decision that caused it, pins that decision (novel fix correct --block --key --value), and recalls System 1 (novel recall): the block re-runs from the stored source with the pin honored and logged, producing a fresh ChangeSet; the superseded one is kept for audit.

Proposals decompose into per-field assertions bound to a revision digest; only accepted, supported facts materialize. Historical changeset facts|decide spellings remain compatibility interfaces outside the scoped Pi host — and even there, source-less packets fail closed. Open questions — the merge gate

  • Revision granularity — ✓ decided 2026-10-26Decided (decision #26): the unit is the per-field fact, bound to a revision digest over packet + source + canonical context. A revision change voids staged state; the remaining question is review presentation at scale (bounded pages of 20), not granularity.
  • Review presentation.How should a packet be summarized for review — counts by kind, lowest-confidence first, new entities spotlighted? The agent reviews faster with the right digest; the user spot-checks with the same view. Bounded paging (20 facts) is the current shape.
  • Lock recovery.A crashed review command leaves its lock dir behind. Timeout, stale-lock detection, or a documented recovery command — one of the three is owed.
  • Auto-approval envelope.Should very high-confidence, low-risk proposal classes (e.g. PRESENT_IN at 0.97) ever skip review in bulk, with the agent auditing samples? Speed vs. the safety property.
  • Cross-block consistency checks.Before approving block N, should the gate run standing queries — duplicate-name suspects, state contradictions — against everything merged so far?

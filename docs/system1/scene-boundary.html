Scene boundary — where scenes start

status: implemented (span selection) repo: src/digger/autostep/patches/scene-boundary.ts model: Jev · choice (span selection)

Scenes are the unit everything else keys off: presence is per-scene, dialogue groups inside scenes, and extraction reads one scene at a time.

Redesigned 2026-10-22 — span selection. The per-sentence design below the line is retired: asking one noul per sentence ("does a scene begin here?") over disjoint 40-sentence windows produced 77 scenes with a median size of ONE sentence on real text. Jev now points: over 80-sentence batches with a 20-sentence look-back it chooses where scenes start; each scene's end is defined by the next chosen start, so scenes tile the block exactly (start = last end + 1). An end-pick per scene serves as cross-check, and a scene open at a batch seam gets one continuation query with its tail text injected. Measured reason starts rule: asked for the end of a scene whose start was imposed, Jev picks the batch's last sentence at 0.95 confidence and the block collapses into one scene; asked to choose starts, it finds the real joints (10 scenes, exact partition, on the same 15K chars). Decision questions

scene_start · choice — Which sentence id BEGINS the next scene at or after the anchor (place change, time skip, viewpoint shift), or NONE? The boundary detector: each chosen start closes the open scene at start − 1.
scene_end · choice — Which sentence id is the LAST sentence of the scene that begins at the given start? Advisory: cross-check (a chosen start far past it flags a possible missed boundary) and the provisional end a seam can ratify.
scene_seam · choice — Shown the open scene's tail text and the following passage: does the scene CONTINUE into it, or did it END before it begins? One query per batch seam; "ended" ratifies the provisional end and the next scene opens at end + 1.
boundary_reason · choice candidate — location_changed / time_skipped / pov_changed / cast_changed. Knowing why a boundary fired helps presence decide carryover.

Design details

  • Block-level prepass — start selection is sequential (each start depends on the last), so this patch runs once over the whole block before the per-window patches; its partition frames everything downstream.
  • Tiling is guaranteed by construction: boundaries derive from chosen starts, so every sentence lands in exactly one scene — no gaps, no overlaps, no window-edge cuts. Uncertain picks escalate to the gate instead of silently cutting.
  • Spans, not copies: a scene is a list of sentence IDs; the text stays in the block, referenced.

Implementation

  • src/digger/autostep/patches/scene-boundary.ts + src/digger/autostep/segmentation.ts — the prepass tiles the block into ctx.accepted.sceneSpans. Decision keys are pinnable for recall: scene_start:<anchorId>, scene_end:<startId>, scene_seam:<firstFollowingId>.
  • Gates: accept ≥ 0.85 · re-ask 0.55–0.85 · escalate < 0.55 (tuning: see Open questions).

Open questions — scene boundaries

  • Granularity.Is a flashback inside a conversation a new scene, or a marked sub-span? Same question for dreams and回忆 interludes. Partially answered (2026-10-26, decision #25): flashbacks are marked on time periods, not cut into scenes — the time-place faculty (08b) gives the scene a TimePoint with a Jev flashback role, and the scene span itself does not change.
  • Soft boundaries.Same room, same cast, but an hour passes — one scene or two? The answer changes how presence carryover works (sector 05).
  • Reason taxonomy.Is {location, time, POV, cast} the right reason set — and does extraction actually consume the reason, or is it decoration?
  • Length caps.Extraction reads per scene; is there a max scene size beyond which a "soft split" is forced for context limits?
